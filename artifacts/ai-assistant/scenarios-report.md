# FactSim AI：10質問の実機検証と修正

実施日：2026-09-27。実際の Ollama `qwen3.8:27b` に、アプリの `FactSimAgent` / Provider / ToolRegistry を通して質問した。回答の差し替え・模擬LLMは使用していない。

隔離した headless Edge のテストページを使用。各質問は simple の4ノード直列ラインから開始し、7番は2ノードを意図的に重ね、10番は実エンジンで120秒実行してから質問した。ユーザーの開いているモデル、Ollama設定、保存済みサンプルには変更していない。グラフ変更の自動承認はテストページだけで有効にした。

## 発見した問題 → 検討 → 実装 → 再確認

1. 挨拶で長い機能一覧を出し、稼働率・待ち時間分布の測定まで案内した。固定応答で置き換えず、挨拶を1–2文にし、KPIツールが取得できる完了数・スループットに案内を限定するルールを実装。実LLMの再回答は短い自然な挨拶になった。
2. 能力説明で、編集ツールにないバッチサイズや確率の変更を案内した。登録済みカタログと編集可能パラメータに限定するルールを実装。再回答から未対応設定の変更案内がなくなった。
3. 停止が再現しなかっただけで「エンジン自体は固まっていない」「UI側の可能性が高い」と説明した。テストしたモード・時間・条件に結論を限定し、未測定候補を根拠なしで順位付けしないルールを実装。再回答は今回の有界ステップ実行で未再現と明示した。
4. ボトルネック調査で既取得のKPIを再取得し、ノード設定を3回個別に読んだ。レポートのKPIを再利用し、設定は `get_nodes` で一括取得するルールを実装。再試行は5呼出から2呼出になった。呼出数の削減であり、総応答時間の一律短縮を保証するものではない。
5. 必須の直列2工程を並列の代替経路に変える改善案を提示した。全必須工程を保った完全ライン複製・同等資源の追加だけを並列増強として提案するルールを実装。再回答では全工程を維持した複製ラインを提案した。
6. 加工時間だけを短縮する案で、変更していない回復時間を計算から落とした。各案を独立に評価し、未変更の全フェーズを残して周期を計算し、組合せ案では前提を明示するルールを実装。最終回答は加工0.5秒＋回復3秒＝3.5秒、理論約1029個/時と正しく計算した。
7. `auto_layout` の説明が、個別修正方針と矛盾して「重なりなら使う」と記載されていた。明示的な全体自動配置依頼だけに限定するツール説明へ変更。実モデルの重なり修正は個別移動を使い、全体自動配置を呼ばなかった。

変更は `system-prompt.js` のモデル向け規則、`factsim-tools.js` のツール説明、script version、実モデル用テストと案内。特定質問への定型回答や、回答文の数値を書き換える処理は追加していない。エンジン本体・既存モデルの設定は変更していない。

## 検証の精度と限界

回答を読むだけでなく、実行されたツール、実グラフ、設定、接続、実測KPIを比較した。文字列による合格判定は補助であり、未対応機能の案内、因果関係の断定、改善案の工程維持、計算の正しさは回答を目視レビューした。初回の緩い自動判定で合格表示された回答でも、目視で問題を発見して判定条件を強化した。

設定不変の強化テストでは、描画用リンクキャッシュとFlowの遅延生成キャッシュを「設定変更」と誤判定した。実際の差分を調査して内部キャッシュのみと確認し、接続は保存用の接続タプル、設定は既知の `__signalCache` / `__feedbackCache` を除いた意味的内容で比較するようテストを修正した。その他のパラメータを比較から除外してはいない。6番・7番を実LLMで再実行して不変条件を確認した。

この検証は simple モデル・eventモードを対象とする。ユーザーの132ノードのモデルが1000秒付近で止まる実原因を特定したものではない。AIの規則への従い方にはばらつきがあり、すべてのモデル・質問の正答を保証しない。
