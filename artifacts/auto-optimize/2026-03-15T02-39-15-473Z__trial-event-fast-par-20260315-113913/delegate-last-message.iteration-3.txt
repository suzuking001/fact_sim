1. Performance hypothesis

The `event-fast-par` host was paying avoidable overhead in its hottest coordination path: every substep and flush round it flattened all worker `emittedMessages` into a temporary array, then rebuilt full bucket arrays just to discover which partitions were actually touched. On cross-partition workloads, reducing those allocations and scans should improve headless throughput.

2. What changed

I only edited [js/app/engine-fast-par-host.js](/C:/Users/suzuk/AppData/Local/Temp/fact-sim-auto-patch/1773543128708-28028/js/app/engine-fast-par-host.js#L288). The old `bucketMessages(messages, partitionCount)` helper was replaced with `bucketWorkerMessages(payloads, partitionCount)`, which buckets directly from worker payloads and returns a `touched` partition list without `flatMap` or preallocating empty buckets for every partition. `_stepParallel` now consumes that helper directly in the step and flush loop at [js/app/engine-fast-par-host.js](/C:/Users/suzuk/AppData/Local/Temp/fact-sim-auto-patch/1773543128708-28028/js/app/engine-fast-par-host.js#L636).

3. Focused verification run

I ran `node --check js/app/engine-fast-par-host.js`.

I ran `engine_test` against `dt` vs `event-fast-par` with `strictFinalParity=true`, `reruns=2`, `stopOnFirstFailure=true` for both `quick` and `standard`. Both passed, including the `parallel_benchmark` scenario, with no failures or warnings.

I also ran a local microbenchmark of the exact bucketing change on synthetic worker payloads. Result: old path `1065.541ms`, new path `410.485ms`, about `+159.58%` for that helper workload. I was not able to get the MCP benchmark API to accept `event-fast-par` mode directly, so I do not have a fresh 500ms end-to-end speed number against the `9726.176x` baseline.

4. Residual risk

The gain is most likely on workloads with frequent cross-partition message exchange; partition-independent graphs will see little or no benefit. End-to-end improvement against the nightly 500ms benchmark still needs confirmation in the full benchmark harness, since the available MCP benchmark entrypoints rejected `event-fast-par` mode even though parity testing worked.
