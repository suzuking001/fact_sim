# dt 高速化の調査

本体を変更せず、dt の更新呼出しに一時的な Flow キャッシュと同期メンバー表を適用して比較した。時間刻み、全ノード実行順序、同時刻の追加実行は元の dt のまま。

条件: 各 example で同じ300,000 msのシミュレーション、update引数10,000 ms、ウォームアップ1回＋計測5回、中央値。描画とタイミングチャート記録は無効。設定毎にグラフと乱数を初期化。準備・キャッシュ検査の時間も計測に含む。

| Example | 元dt (ms) | 同期メンバー表のみ | Flowキャッシュのみ | 併用 |
| --- | ---: | ---: | ---: | ---: |
| sample_line2 | 4591.1 | 3.80倍 | 1.05倍 | 4.63倍 |
| sample_line1 | 437.2 | 1.00倍 | 1.34倍 | 1.33倍 |
| parallel_benchmark | 128.8 | 0.97倍 | 1.22倍 | 1.20倍 |
| carrier | 79.8 | 1.04倍 | 1.35倍 | 1.30倍 |

最も効果が大きかったのは Sample Line2 の同期メンバー探索を事前計算する方法（3.80倍）。Flow 内の接続索引、配列割り当て削減、履歴索引、Source の数量を展開しない選択を併用すると4.63倍。同期グループを持たない例では同期の変更だけでは改善せず、Flow キャッシュが1.22〜1.35倍だった。

全計測で最終の __flowRuntime は元dtと完全一致した。任意のカスタムスクリプト、実行中のモデル編集、タイミングチャート、canonical entity ledger、全 example の正式な Engine Test parity は今回の試行では検証していない。dt/engine.jsへの恒久的な変更はない。

さらに大きな改善候補は、固定刻みを保ちつつ、変更・期限到達・入力変化のない既知の標準ノードの実行を省略する方法。ただし依存関係・同期・同時刻処理を正しく追跡する必要があり、任意スクリプトには毎刻み実行を残す必要がある。この方式の改善率は未計測。
