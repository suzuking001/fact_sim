# event-fast-par 通常実行の速度低下を修正

確認日: 2026-09-28。

## 修正結果

実際のアプリのstartSimulation / startSimLoopとFASTEST設定を使って、約5倍しか進まない現象を再現した。修正後、同じ環境・同じサンプルの画面上の速度表示は以下のように改善した。

| サンプル | 修正前 | 修正後 | 修正前に対する速度 | 改善率 |
| --- | ---: | ---: | ---: | ---: |
| sample_line2 | 5.44倍 | 952.8倍 | 175.15倍 | +17,414.7% |
| parallel_benchmark | 23.16倍 | 1,624倍 | 70.12倍 | +6,912.1% |

値は各3回の中央値。各回、最新ページで例を読み込み、FASTESTで約1.5秒間実行した。表はアプリの直近1秒の速度表示（シミュレーション時間 / 実時間）を利用しており、起動時間・実行全体の平均値とは異なる。FASTESTでは既存の仕様どおり描画を抑制している。環境やグラフにより速度は変わる。

修正後の停止は36〜128ms程度の初回確認、最終測定では45〜86msだった。別の回帰テストでは約109msだった。修正前のベンチマークだけは停止時に合成された待ち時間を検証スクリプトで破棄し、未修正版が大量の未実行時間を消化し続けないようにした。測定中の速度には影響しない。

## 原因と変更

- FASTESTでも100msのシミュレーション時間ごとにWorkerを呼び、毎回全グラフの状態を取得・統合していた。独立区画は最大10,000msまでまとめて計算するよう変更した。
- メインループが大量に投入するFASTESTの要求を無制限に蓄積していた。修正前の1.5秒の測定では約18億ms（約21日分）の未実行要求が残った。FASTESTの待ち行列を2バッチ以内に制限し、停止時は未実行の合成要求を破棄する。
- FASTESTの全状態取得を実時間120ms程度ごとにし、計算の途中の状態遷移はWorkerから軽量な履歴として送信する。単純なsnapshotの間引きで履歴を失うことを避ける。
- 速度指定が高い通常モードでも、複数の処理待ちがある場合にまとめて計算する。通常速度の小さな刻みは従来の経路を維持する。
- 停止時は実行中のWorker処理と最終状態取得を待ち、最終状態を画面に反映する。別の実行を開始した場合に古い実行結果が上書きしないようにした。
- legacy Flowのポート・配線を正規化した結果を、Workerへの分割と最終snapshotの統合の両方に使用する。carrierとsample_line1で有効なリンクが消えていた不具合を修正した。
- アプリのscriptとWorker URLのversionを更新し、新しい実装を読み込めるようにした。

dt / event (heap) / engine.jsは変更していない。サンプルやAI設定にあった作業開始前の変更もそのまま保持した。

## 検証

- 変更したJSと回帰確認スクリプトのnode --check: PASS
- mcp/npm run check: PASS
- mcp/npm run build: PASS
- Engine Test quick、全5エンジン・全8example・seed=[1,12345]・strictFinalParity=true: **80/80 PASS、警告0**
- completion / visible flow / ノード状態遷移 / timing chart / strict final parityの比較を実施した。
- 追加のlive回帰確認: simple / parallel_benchmark / sample_line2を30,000msまで進め、通常の100ms要求・通常の10,000ms要求・FASTEST要求について完成数・最終ノード状態・Entity状態が一致した。状態遷移がタイミングチャートに残り、区間が逆行しないことも確認した。
- ノードのオブジェクト同一性、リンク数、live同期エラーなし、FASTESTの待ち行列上限、停止後の時刻安定、停止時のgraph statusを確認した。
- 実際の128倍指定による500msの実行では、停止要求前に66,100ms、停止処理後に70,412.8msまで進んだ。100msごとに要求する制限で約5倍になる現象は解消した。
- 各確認はruntimeを再読み込みして実施した。
